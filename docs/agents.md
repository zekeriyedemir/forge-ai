# Agents

Founder → Research → Founder review → Developer → Analyst is the V1 sequence. The founder creates strategy and tasks, research drafts a market research outline, the second founder pass reviews new context, the developer creates an MVP plan, and the analyst records risks and next actions.

Every run has an ID, workflow ID, step, agent type, input, status, structured output, events, provider/model metadata, timestamps, and error. One shared Zod contract validates provider output and tool inputs before content is written. Readable metric names are normalized to bounded lowercase snake_case keys; unsafe keys and duplicate normalized keys fail validation. An existing metric's key cannot be reused with a different label or unit. The provider interface can be extended without changing the runtime.

The demo provider uses deterministic templates. Its market content is explicitly labeled unverified. The live OpenAI-compatible provider uses Chat Completions JSON mode, an explicit field contract, and at most one regeneration attempt for malformed output. Complete fenced JSON is accepted, but prose or invalid JSON is not. It has no external research tool, so it must not claim to have checked market facts. Automated tests use fake responses and do not call a paid provider.

## Developer repository execution

The existing Founder → Research → Founder review → Developer → Analyst workflow still creates Forge tasks and reports. Repository execution is a separate, owner-initiated step for one of those tasks. In **Project → Approval Center**, select a task after linking a GitHub repository. Forge reads the repository identity, selects `dev` when it exists (otherwise the repository default branch), reads a bounded tree and selected small source/config files, and asks the live OpenAI-compatible model for a structured proposal. The proposal contains the task, summary, complete proposed file contents, reasons, validation plan, risks, and a conventional commit message. The entire proposal is Zod-validated and displayed before approval. Malformed model output gets one regeneration attempt; no repository write occurs during proposal generation.

An owner with a real GitHub session approves the **IMPLEMENT** request. Forge then creates a `forge/<task-slug>-<8-char-id>` branch, creates a Git tree and commit attributed to **Forge AI Developer**, updates only that feature branch without force, and opens a PR. The PR targets `dev` when present, otherwise the verified default branch. Forge stores branch, target, base/commit SHA, PR number/URL/state, progress, and validation summary. It creates a separate **MERGE** request; PR creation never merges automatically. The approver can reject either request.

Approval states are `PENDING`, `APPROVED`, `EXECUTING`, `REJECTED`, `EXECUTED`, and `FAILED`. An approved operation is claimed atomically before any write. An explicit retry can reclaim a failed operation; an in-progress claim becomes retryable after fifteen minutes. Forge re-reads the branch and PR to avoid duplicate branches, referenced commits, and PRs. It persists the commit SHA before moving the branch. If the feature branch differs from the stored base/commit SHA, execution stops for manual review. A failure displays its persisted stage and safe error; it is never reported as success. If a failure occurs after creating a Git object but before persisting its SHA, GitHub may retain an unreferenced object. The retry does not rewrite history or force-push.

Merge execution re-fetches the PR, verifies both sides belong to the linked repository, compares the approved head SHA and target/feature branch, requires an open and mergeable PR and at least one passing GitHub check/status, and calls GitHub's merge API with the head SHA precondition. GitHub branch protection remains authoritative. Pending, missing, or failing checks block merge; retry after checks pass. If someone changes the PR head after approval, Forge rejects the stale approval and stops. Review the changed PR on GitHub and create a new Forge task/proposal rather than reusing that approval.

Forge does not execute model-generated shell commands or run the target repository's tests on its own infrastructure. Proposal validation checks structure, allowed paths, file sizes, text content, and inspected-file coverage. Repository tests must run in GitHub CI after the PR is opened; the Approval Center labels this distinction. Configure at least one CI check for the repository before using Forge's merge action.

If proposal generation fails before an approval exists, Forge records a sanitized `developer-proposal-failed` activity event and shows the latest failures in the Approval Center. The stage and code distinguish GitHub inspection, branch/base resolution, repository limits, AI connectivity, malformed structured output, final proposal validation, and database persistence. Server logs contain only these safe classifications, project/task IDs, and fixed explanatory text; they never include tokens, provider response bodies, database URLs, or source-file contents. An earlier failure from a version without these diagnostics cannot be reconstructed; retry the proposal after updating to see its specific stage.
