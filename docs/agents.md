# Agents

Founder → Research → Founder review → Developer → Analyst remains the workflow sequence. The founder creates strategy and tasks. In live mode, Research searches and retrieves bounded public evidence, saves source-backed findings and a cited report, and the second founder pass consumes those findings. In demo mode Research still produces a labeled unverified outline. The developer creates an MVP plan, and the analyst records risks and next actions.

Every run has an ID, workflow ID, step, agent type, input, status, structured output, events, provider/model metadata, timestamps, and error. One shared Zod contract validates provider output and tool inputs before content is written. Readable metric names are normalized to bounded lowercase snake_case keys; unsafe keys and duplicate normalized keys fail validation. An existing metric's key cannot be reused with a different label or unit. The provider interface can be extended without changing the runtime.

The demo provider uses deterministic templates. Its market content is explicitly labeled unverified. Ordinary live agents use Chat Completions JSON mode and one regeneration attempt for malformed output. Live Research instead uses a controlled Brave Search adapter and public-page retriever, then asks the configured AI provider for structured findings. Each finding must cite a saved source and quote exact retrieved text; missing evidence fails before any finding is persisted. The model does not control search URLs, retrieval, or permissions. The later Founder prompt receives only findings from a completed session in the same workflow and treats quotes as untrusted data. See [Research](research.md) for limits and failure behavior. Automated tests mock search, pages, and AI; they do not spend provider credits.

## Developer repository execution

The existing Founder → Research → Founder review → Developer → Analyst workflow still creates Forge tasks and reports. Repository execution is a separate, owner-initiated step for one of those tasks. In **Project → Approval Center**, select a task after linking a GitHub repository. Forge reads the repository identity, selects `dev` when it exists (otherwise the repository default branch), and ranks a tree of at most 500 entries against the task. It reads at most ten relevant text files (12 KB each, 64 KB total), prioritizing source, related tests, configuration, and nearby relative imports. It records the paths actually inspected. The live OpenAI-compatible model must return a structured proposal with complete final file contents, explicit CREATE/UPDATE operations, reasons, a validation plan, expected CI success, risks, and a conventional commit message. Forge validates this with Zod and checks each UPDATE against the inspected contents. Existing persisted proposals without operation labels remain readable for in-flight PR #5 approvals. Malformed model output gets one regeneration attempt; no repository write occurs during proposal generation.

An owner with a real GitHub session approves the **IMPLEMENT** request. Forge then creates a `forge/<task-slug>-<8-char-id>` branch, creates a Git tree and commit attributed to **Forge AI Developer**, updates only that feature branch without force, and opens a PR. The PR targets `dev` when present, otherwise the verified default branch. Forge stores branch, target, base/commit SHA, PR number/URL/state, progress, and validation summary. It creates a separate **MERGE** request; PR creation never merges automatically. The approver can reject either request.

Approval states are `PENDING`, `APPROVED`, `EXECUTING`, `REJECTED`, `EXECUTED`, and `FAILED`. An approved operation is claimed atomically before any write. An explicit retry can reclaim a failed operation; an in-progress claim becomes retryable after fifteen minutes. Forge re-reads the branch and PR to avoid duplicate branches, referenced commits, and PRs. It persists the commit SHA before moving the branch. If the feature branch differs from the stored base/commit SHA, execution stops for manual review. A failure displays its persisted stage and safe error; it is never reported as success. If a failure occurs after creating a Git object but before persisting its SHA, GitHub may retain an unreferenced object. The retry does not rewrite history or force-push.

Merge execution re-fetches the PR, verifies both sides belong to the linked repository, compares the approved head SHA and target/feature branch, requires an open and mergeable PR and at least one passing GitHub check/status, and calls GitHub's merge API with the head SHA precondition. GitHub branch protection remains authoritative. Pending, missing, or failing checks block merge; retry after checks pass. If someone changes the PR head after approval, Forge blocks the execution until that external head is explicitly reviewed and adopted. Old merge approvals remain unusable and are rejected on adoption.

Forge does not execute model-generated shell commands or run the target repository's tests on its own infrastructure. Proposal validation checks structure, allowed paths, file sizes, text content, operation labels, and inspected-file coverage. Repository tests must run in GitHub CI after the PR is opened; the Approval Center labels this distinction. Configure at least one CI check for the repository before using Forge's merge action.

After PR creation, **Refresh CI** reads check runs and commit statuses for the stored head SHA and persists pending, success, failure, cancelled, or unavailable, with names shown only when they pass a strict safe-label filter. If the PR or feature-branch head changed externally, it instead records `EXTERNAL_CHANGE`, the Forge-known and current GitHub SHAs, and clears stale CI success. Correction and merge actions are blocked. **Review & adopt external head** prepares an **ADOPT** request showing the PR, branch, target, and exact old/new SHAs. The owner reviews the GitHub diff and separately approves it. Forge rechecks repository identity, open PR, branch, target, and exact GitHub SHA immediately before adoption, refreshes CI for that SHA, records the commit as externally supplied, rejects old merge/fix approvals, and creates a fresh merge request. Adoption reads GitHub but does not push or merge. A second external change makes the old adoption request stale and requires another refresh and review.

The separate merge gate still performs its own fresh check. On failure, **Analyze failure & propose correction** verifies the same open PR and adopted head, reads a bounded failing Actions job/step, and requests at most 32 KB of one job log. Forge reduces those log bytes locally to safe diagnostic categories, TypeScript codes, and validated repository paths; raw log lines and signed log URLs are never saved or sent to the model. If logs are unavailable, job/step and failed-check metadata may still support a proposal. The model returns a Zod-validated CI correction with failure summary, likely cause, complete CREATE/UPDATE files, risks, and expected validation result. No GitHub write occurs until the owner approves the new **FIX** request.

On approval, Forge rechecks repository identity, open PR, target, feature branch, and exact approved base SHA. It creates a new commit on the same `forge/` branch with a non-force update; the existing PR receives the new head. Forge records the correction round, previous/new SHA, and a fresh merge approval tied to that head. Old merge approvals cannot merge a corrected head. At most three correction requests are allowed per execution, and a later CI failure requires another explicit proposal and approval. A stale branch or PR stops the correction before a new commit is created. Refresh CI again after GitHub runs checks; passing CI does not merge automatically.

If proposal generation fails before an approval exists, Forge records a sanitized `developer-proposal-failed` activity event and shows the latest failures in the Approval Center. The stage and code distinguish GitHub inspection, branch/base resolution, repository limits, AI connectivity, malformed structured output, final proposal validation, and database persistence. Server logs contain only these safe classifications, project/task IDs, and fixed explanatory text; they never include tokens, provider response bodies, database URLs, or source-file contents. An earlier failure from a version without these diagnostics cannot be reconstructed; retry the proposal after updating to see its specific stage.

Developer proposals use `DEVELOPER_PROPOSAL_MAX_COMPLETION_TOKENS` (default `8192`, allowed `1024`–`32768`) in the Chat Completions request. This budget is separate from ordinary Forge agent responses. Choose a model whose output and context limits can hold the selected repository files plus complete proposed file contents; some models support less than the default and require a lower setting. A length stop discards the partial response and makes one fresh attempt asking for the smallest complete change. Repeated truncation reports `TRUNCATED`; empty text reports `EMPTY_CONTENT`, invalid JSON reports `MALFORMED_JSON`, and an oversized repository context reports `CONTEXT_TOO_LARGE` when the provider identifies it. Forge never accepts partial JSON or file contents. If the proposal does not fit, choose a smaller task or a model with a larger context/output limit. The configured provider's real behavior must be checked manually; tests use fake responses.

The Developer adapter accepts a non-streaming Chat Completion with a text string (or text-only content parts) in the first assistant message. Extra usage, routing, and reasoning metadata do not change the final-text requirement. Missing or empty `choices`, an absent assistant message, unsupported content types, and reasoning/tool/refusal output without final text fail before proposal validation; unusable envelope shapes are not sent through the JSON repair loop. Their activity event contains only safe structural facts: HTTP status, choices count, message/content types, allowlisted finish reason, a restricted model slug when present, and boolean usage/reasoning/tool/refusal indicators. It never records prompts, returned text, file contents, headers, or credentials. With `OPENAI_MODEL=openrouter/free`, OpenRouter can select a different free model on each request, so record the sanitized response-model slug from the event when diagnosing a failure. To retest, restart Forge with this branch, open the linked project's **Approval Center**, select the same task, and click **Inspect repository and propose**. If it fails, copy only the stage, code, and `Response structure` facts from the latest project activity event. If it succeeds, review the proposed files; generation itself makes no GitHub write.
