# Security

Auth.js stores sessions in PostgreSQL and GitHub OAuth credentials stay on the server. A GitHub access token is read from the Account table only inside server code. Repository association re-checks the repository against the authenticated user's GitHub API response; a client-supplied name or URL is never trusted.

Project reads require workspace membership; project mutations require an `OWNER` membership on server actions and API routes. Forms and tool inputs use Zod. Workflow starts are limited to five per project per hour as a basic cost guard. Configure a unique `AUTH_SECRET`, HTTPS, and database credentials in the deployment environment. `DEMO_MODE=true` intentionally allows public access to a shared demo account; use it only with disposable data and a dedicated database. Disable it for private production workspaces.

Developer repository writes require a real authenticated GitHub session, project ownership, an exact linked-repository identity, and a persisted approval. The OAuth app uses the `repo` scope for private/public repository read/write access; organization policies can still deny access. GitHub tokens remain server-side and are not sent to the model or browser. Approved source changes are limited to five text files, 32 KB per file, 64 KB total, and 500 repository files inspected. Hidden paths, traversal, binary content, credential-like content, and files outside source/test/docs roots are rejected. Existing files may be replaced only if Forge read their full original contents. Branch writes are restricted to generated `forge/` branches and are never forced. Merge requires a separate approval and passing remote checks.

The repository inspection filters obvious credential material, but no static filter can guarantee that arbitrary source text contains no secrets. Use a repository without committed secrets and review the exact proposal before approval. Forge never reads local `.env` or gives the model access to server environment variables. The GitHub OAuth `repo` scope is broad; a dedicated GitHub App with repository-scoped permissions is a future hardening option. The Developer workflow does not run target code or model-provided commands on the Forge server.

Current limitations: no distributed rate limiter, no token encryption beyond database and infrastructure controls, and no automatic reconciliation of externally modified feature branches or pull requests. `DEMO_MODE=true` still supports the existing business-planning workflow; repository execution requires real GitHub sign-in and a live AI provider.
